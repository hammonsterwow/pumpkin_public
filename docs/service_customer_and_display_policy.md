# 고객 유형 및 화면 역할 기준

> 상태: **현재 서비스 기획 기준 (Current Policy)**  
> 최종 정리일: 2026-08-14  
> 대상: 고객용 앱, 주문 서버, 로봇 응대, 사장님용 POS 웹, 시연 웹, 로봇 가슴 모니터 화면

이 문서는 Pumpkin 프로젝트에서 **고객 유형에 따라 어떤 서비스가 동작해야 하는지**와 **각 화면/웹의 역할을 어디까지로 제한할지**를 정한 기준 문서다.

팀원 및 ChatGPT/Codex가 관련 기능을 구현·수정할 때는 이 문서를 먼저 확인한다.

---

## 1. 가장 중요한 서비스 원칙

### 1.1 `사전주문`과 `단골`은 서로 독립된 상태다

고객을 단순히 회원/비회원 두 종류로 나누지 않는다.

서비스 판단에는 다음 두 조건을 **서로 독립적으로** 본다.

- **단골 등록 여부**: 얼굴 등록 및 개인화 서비스 사용 여부
- **현재 사전주문 여부**: 앱에서 현재 유효한 주문을 넣었는지 여부

따라서 다음 네 가지 경우가 모두 존재한다.

```text
                    사전주문 없음          사전주문 있음
단골 아님           ① 일반 시민            ③ 사전주문만
단골 맞음           ② 단골                 ④ 사전주문 + 단골
```

### 1.2 앱 회원가입과 단골 등록도 같은 개념이 아니다

- 앱 계정을 만들었다고 자동으로 단골 고객이 되는 것이 아니다.
- 얼굴 등록/개인화 서비스에 등록해야 단골 고객으로 취급한다.
- **사전주문 기능 사용에 단골 등록을 강제하지 않는다.**
- 따라서 얼굴 등록을 하지 않은 앱 사용자도 사전주문할 수 있다.

# 2. 고객 유형별 서비스 정책

## 2.1 유형 1 — 일반 시민

### 조건

- 단골 등록 없음
- 현재 사전주문 없음

### 로봇 동작

일반 고객과 동일하게 응대한다.

```text
고객 접근
→ 사람 감지
→ 일반 인사
→ 음성 주문 시작
→ STT / NLU / Decision
→ 주문 확인 및 재질문
→ 주문 완료
```

### 개인화

없음.

- 이름 언급 안 함
- 선호 메뉴 언급 안 함
- 과거 주문 이력 기반 추천 안 함

---

## 2.2 유형 2 — 단골 고객

### 조건

- 단골 등록 완료
- 현재 사전주문 없음

### 로봇 동작

얼굴 인식으로 등록 고객을 식별한 뒤 **개인화 응대**를 제공한다.

대표 동작:

```text
고객 접근
→ 얼굴 인식
→ 단골 고객 식별
→ 선호 메뉴/주문 이력 확인
→ 개인화 인사
→ 선호 메뉴 언급
→ 현장 음성 주문 진행
```

### 핵심 기능

**선호 메뉴를 언급하는 것**이 단골 응대의 핵심 시연 포인트다.

예시:

```text
"안녕하세요. 평소 드시던 아이스 아메리카노로 주문하시겠어요?"
```

단골이라고 해서 자동 주문 확정하지 않는다. 사용자의 확인 또는 실제 주문 입력을 받아 주문을 진행한다.

---

## 2.3 유형 3 — 사전주문만 한 고객

### 조건

- 단골 등록 없음
- 앱에서 사전주문 완료

### 로봇 동작

**사전주문을 했다는 이유만으로 로봇이 특별히 반응하지 않는다.**

즉 다음 기능은 수행하지 않는다.

- 고객 자동 식별
- 사전주문 내역 자동 언급
- 주문 메뉴를 로봇이 먼저 안내
- 픽업 위치를 로봇이 먼저 안내

사전주문만 한 고객에 대한 핵심은 **앱 → 주문 서버 → POS 웹 → 앱 주문 상태** 흐름이다.

### 사전주문 처리 흐름

```text
고객 앱에서 주문
→ 주문 서버에 주문 생성
→ POS 웹에 새 주문이 실시간 표시
→ 사장님/관리자가 주문 상태 변경
→ 변경된 주문 상태가 앱에 실시간 반영
→ 고객이 앱에서 진행 상태 확인
```

### 이 유형의 구현 범위

필수:

- 앱에서 사전주문 생성
- POS 웹에 주문 실시간 등록
- 주문 상태 관리
- 앱에 주문 처리 과정 실시간 표시

로봇 개인화 연동은 하지 않는다.

---

## 2.4 유형 4 — 사전주문 + 단골 고객

### 조건

- 단골 등록 완료
- 앱에서 현재 유효한 사전주문 존재

### 로봇 동작

이 유형이 **사전주문과 얼굴 인식이 실제 로봇 서비스로 연결되는 대표 시나리오**다.

```text
앱에서 사전주문 완료
→ 주문 서버/DB 저장
→ POS 웹에 주문 표시
→ 고객 매장 방문
→ 로봇 카메라가 얼굴 인식
→ 등록 고객 식별
→ 해당 고객의 현재 사전주문 조회
→ 주문 내용 확인
→ 로봇이 픽업 안내
```

### 대표 응대

예시:

```text
"주문하신 아이스 아메리카노가 준비되었습니다. 픽업대에서 가져가 주세요."
```

또는 주문 상태가 아직 제조 중이면 상태에 맞는 안내를 할 수 있다.

중요한 점은 **얼굴 인식 결과만으로 메뉴를 추측하는 것이 아니라, 식별된 customer_id와 실제 사전주문 데이터를 연결해 주문을 조회하는 것**이다.

# 3. 고객 유형 판단 로직

서비스 계층에서는 아래 두 값을 기준으로 현재 고객 상태를 판단한다.

```text
is_regular        # 단골 등록 여부
has_active_order  # 현재 유효한 앱 사전주문 존재 여부
```

판단표:

| is_regular | has_active_order | 고객 유형 | 로봇 처리 |
|---|---|---|---|
| false | false | 일반 시민 | 일반 응대 |
| true | false | 단골 | 선호 메뉴 기반 개인화 응대 |
| false | true | 사전주문만 | 사전주문 때문에 별도 로봇 응대하지 않음 |
| true | true | 사전주문 + 단골 | 얼굴 식별 → 사전주문 조회 → 픽업/주문 상태 안내 |

> `is_regular` 하나로 사전주문 권한을 결정하지 않는다.

# 4. 화면/웹 종류와 역할

Pumpkin 프로젝트의 화면은 목적이 서로 다르므로 하나로 합치지 않고 역할을 분리한다.

```text
① POS 웹       : 실제 주문 운영 확인
② 시연 웹      : 시연영상용 로봇 내부 상태 시각화
③ 모니터 웹    : 로봇 가슴 5인치 화면용 고객 인터페이스
④ 고객 앱      : 사전주문 및 주문 상태 확인 / 단골 등록
```

---

## 4.1 POS 웹 — 사장님/관리자용

### 가장 중요한 목적

> **"주문이 실제로 들어왔구나"를 눈으로 보여주는 것**

사전주문 또는 로봇 주문이 서버에 생성되면 POS 웹에 **실시간으로 주문이 들어오는 모습**이 보여야 한다.

### 사용자

- 카페 사장님
- 관리자
- 시연 시 주문 서버 연동을 확인하는 사람

### 핵심 기능

- 신규 주문 실시간 표시
- 주문 상세 확인
- 주문 유형 구분
  - 로봇 현장 주문
  - 앱 사전주문
- 주문 상태 변경
- 진행 중 주문 확인
- 완료/지난 주문 확인

### 역할 범위

POS 웹은 **운영 화면**이다.

따라서 NLU 내부 추론 과정, 카메라 추적 화면, ROS2 디버그 로그 등을 메인 기능으로 넣지 않는다.

---

## 4.2 시연 웹 — 영상 촬영용

### 목적

> 로봇이 지금 무엇을 보고, 듣고, 인식하고, 판단하는지 **실시간으로 시각화하여 시연영상에 담기 위한 화면**

실제 매장 운영용 웹이 아니라 **프로젝트 시연과 영상 촬영을 위한 전용 화면**이다.

### 보여줄 수 있는 정보 예시

- 카메라 실시간 영상
- 사람 감지 상태
- STT 인식 문장
- NLU 분석 결과
- 메뉴 / 온도 / 수량 슬롯
- 현재 FSM/Decision 상태
- 로봇이 선택한 행동
- 표정/고개/팔 출력 상태

### POS 웹과 합치지 않는 이유

시연 웹은 카메라 영상과 로봇 내부 상태를 지속적으로 실시간 갱신해야 하므로 화면 및 통신 부하가 커질 수 있다.

**POS 웹의 주문 운영 기능이 시연용 실시간 시각화 때문에 무거워지는 것을 피하기 위해 두 웹을 분리한다.**

따라서:

```text
POS 웹   = 실제 주문 운영 확인
시연 웹  = 실시간 AI/로봇 상태 시각화
```

으로 역할을 분리한다.

---

## 4.3 모니터 웹 — 로봇 가슴 5인치 화면

### 목적

로봇을 사용하는 고객이 **지금 말해도 되는지**, **로봇이 무엇을 알아들었는지**, **현재 주문이 어디까지 구성되었는지** 바로 확인할 수 있도록 한다.

이 화면은 개발자용 디버그 화면이 아니라 **고객 인터페이스**다.

### 필수 표시 정보

#### A. 현재 대화 상태

예:

- 대기 중
- 지금 말씀해 주세요
- 듣는 중
- 음성을 확인하는 중
- 주문 확인 중
- 주문 완료

사용자가 **언제 말해야 하는지 타이밍을 알 수 있어야 한다.**

#### B. 자막

로봇과 사용자의 대화 내용을 짧고 읽기 쉽게 표시한다.

예:

```text
고객: 아이스 아메리카노 두 잔 주세요.
로봇: 아이스 아메리카노 두 잔 맞으신가요?
```

#### C. NLU 주문 슬롯

고객이 로봇이 어디까지 정확히 알아들었는지 확인할 수 있도록 다음 정보를 표시한다.

```text
메뉴
온도
수량
```

예:

```text
아메리카노
ICE
2잔
```

아직 알아듣지 못한 값은 임의로 채우지 않는다.

예:

```text
메뉴     아메리카노
온도     선택 필요
수량     2잔
```

이렇게 표시하면 고객도 로봇이 **온도를 아직 못 들었다는 것**을 바로 알 수 있다.

#### D. 복수/추가 주문 표시

추가 주문으로 주문 항목이 두 개 이상이면 **주문 항목을 각각 별도의 리스트/카드로 보여준다.**

예:

```text
주문 1
아메리카노 / ICE / 2잔

주문 2
카페라떼 / HOT / 1잔
```

하나의 메뉴/온도/수량 영역에 여러 주문을 섞어 표시하지 않는다.

# 5. 화면별 데이터 관점

| 화면 | 가장 중요한 데이터 | 주 사용자 | 목적 |
|---|---|---|---|
| 고객 앱 | 메뉴, 사전주문, 주문 상태, 단골 등록 | 고객 | 주문 및 상태 확인 |
| POS 웹 | 주문 목록, 주문 상태 | 사장님/관리자 | 주문 운영 |
| 시연 웹 | 카메라, STT, NLU, Decision, 로봇 Action | 시연자/심사자 | 실시간 동작 설명 |
| 모니터 웹 | 대화 상태, 자막, 메뉴/온도/수량 슬롯 | 로봇 앞 고객 | 상호작용 보조 |

# 6. 전체 서비스 예시

## 시나리오 A — 일반 현장 주문

```text
일반 시민 접근
→ 로봇 일반 인사
→ 가슴 모니터: "지금 말씀해 주세요"
→ 고객 음성 주문
→ 가슴 모니터: 인식된 메뉴/온도/수량 표시
→ 주문 확인
→ 주문 서버 저장
→ POS 웹에 신규 주문 실시간 표시
```

## 시나리오 B — 단골 현장 주문

```text
단골 고객 접근
→ 얼굴 인식
→ 고객 식별
→ 선호 메뉴 조회
→ 로봇이 선호 메뉴 언급
→ 고객 확인/새 주문
→ 가슴 모니터에 주문 슬롯 표시
→ POS 웹에 주문 등록
```

## 시나리오 C — 사전주문만

```text
앱 사용자 사전주문
→ 주문 서버 저장
→ POS 웹에 신규 주문 실시간 표시
→ 관리자가 주문 상태 변경
→ 앱에 진행 상태 실시간 반영
```

이 시나리오에서는 **사전주문 자체로 로봇의 특별 응대를 발생시키지 않는다.**

## 시나리오 D — 사전주문 + 단골

```text
단골 고객이 앱에서 사전주문
→ 주문 서버 저장
→ POS 웹에 주문 표시
→ 고객 매장 방문
→ 로봇 얼굴 인식
→ customer_id 확인
→ 해당 고객의 활성 사전주문 조회
→ 주문 상태 확인
→ 로봇이 픽업 안내
```

# 7. 구현 시 지켜야 할 경계

1. **사전주문 기능에 얼굴 등록을 강제하지 않는다.**
2. 앱 회원과 단골 고객을 같은 개념으로 취급하지 않는다.
3. 사전주문만 한 고객에게 얼굴 인식 기반 로봇 서비스를 기대하지 않는다.
4. 얼굴 인식으로 고객을 식별했더라도 실제 주문 내용은 주문 서버/DB에서 조회한다.
5. POS 웹은 주문 운영 중심으로 유지한다.
6. 시연 웹의 실시간 AI/카메라 시각화를 POS 웹에 무리하게 합치지 않는다.
7. 가슴 모니터에는 개발자용 로그보다 **고객이 대화 타이밍과 인식 결과를 이해하는 데 필요한 정보**를 우선 표시한다.
8. 주문 슬롯이 누락되었으면 모니터에서도 임의의 값으로 표시하지 않는다.
9. 복수 주문/추가 주문은 주문 항목별로 분리하여 보여준다.

---

# 8. ChatGPT / Codex가 먼저 읽어야 할 요약

Pumpkin의 고객 서비스 정책을 수정하거나 관련 코드를 구현할 때 다음을 전제로 한다.

```text
- 단골 여부와 사전주문 여부는 독립적이다.
- 일반 시민: 일반 로봇 응대.
- 단골: 얼굴 인식 후 선호 메뉴를 언급하는 개인화 응대.
- 사전주문만: POS 웹과 앱 주문 상태만 연동하며 로봇은 특별 응대하지 않음.
- 사전주문 + 단골: 얼굴 인식 → 해당 고객의 활성 사전주문 조회 → 픽업 안내.

- POS 웹: 사장님용 주문 운영 화면. 주문이 실시간 들어오는 것을 보여주는 것이 핵심.
- 시연 웹: 영상 촬영용. 카메라/STT/NLU/Decision/Action의 실시간 상태를 보여줌.
- 모니터 웹: 로봇 가슴 5인치 고객 화면. 말할 타이밍, 자막, 메뉴/온도/수량 슬롯을 표시.
- 복수 주문은 항목별 리스트로 분리해서 표시.
```

기능 구현 전에 이 정책과 실제 코드가 충돌하면 **임의로 둘 중 하나를 선택하지 말고, 현재 정책 기준은 이 문서임을 명시하고 충돌 지점을 확인한다.**
