# Pumpkin 통합 서비스 시나리오 문서

> 기준 브랜치: `main`  
> 작성 목적: 현재 Pumpkin 프로젝트에서 구현·테스트·설계된 고객 응대 흐름을 하나의 시나리오 기준서로 통합한다.  
> 범위: 일반 고객, 단골 고객, 직접 음성 주문, 누락 슬롯, 다중 수량/복수 메뉴, 확인·수정·취소, 비언어 제스처, STT/NLU 예외, 사전 주문, 픽업/시설 안내.

---

## 1. 문서 사용 원칙

이 문서는 발표용 대본이 아니라 **개발·통합 테스트·시연 준비에서 공통으로 사용하는 서비스 시나리오 기준서**이다.

현재 동작의 기준은 다음 구성요소이다.

- 대화/FSM: `decision_node.py`, `order_dialogue_manager.py`
- 주문 해석: `nlu_node.py`, `nlu_postprocess.py`, `dialogue_slots.py`
- 응답 생성: `response_manager.py`
- 로봇 행동: `action_node.py`
- 사용자 감지·고개 제스처: `vision_node.py`, `head_gesture_recognizer.py`
- 얼굴 식별·개인화: `realtime_face_recognition.py`, `face_identity.py`, `face_personalization_node.py`
- 메뉴 기준: `config/menu_catalog.json`
- 사전 주문/주문 저장: `cloud_relay/`, `apps/customer-mobile/`, `apps/pos-web/`

### 시나리오 상태 표기

- **[현재 핵심 흐름]**: main의 주문 FSM/테스트에 직접 반영된 시나리오
- **[연동 흐름]**: 코드와 서비스 구조는 존재하지만 실제 시연 전 E2E 점검이 필요한 시나리오
- **[운영 정책]**: 시스템이 지켜야 할 예외 처리 및 검증 규칙

## 2. 현재 메뉴 Single Source of Truth

| menu_id | 메뉴 | HOT | ICE | 가격 |
|---:|---|:---:|:---:|---:|
| 1 | 아메리카노 | O | O | 3,000원 |
| 2 | 카페라떼 | O | O | 4,000원 |
| 3 | 바닐라라떼 | O | O | 4,500원 |
| 4 | 레몬에이드 | X | O | 4,500원 |
| 5 | 딸기스무디 | X | O | 5,000원 |

### 메뉴 처리 원칙

1. 아메리카노·카페라떼·바닐라라떼는 온도를 말하지 않으면 로봇이 질문한다.
2. 레몬에이드·딸기스무디는 ICE만 가능하므로 온도를 별도로 질문하지 않는다.
3. 수량을 말하지 않았다고 임의로 1잔으로 채우지 않는다.
4. 주문은 `menu + quantity + temperature(필요한 메뉴)`가 모두 유효해야 최종 확인으로 넘어간다.
5. 동일 메뉴·동일 온도는 합칠 수 있고, 동일 메뉴라도 온도가 다르면 별도 주문 항목으로 유지한다.
6. 현재 수량 정책은 항목당 1~20잔이다.

# 3. 고객 진입 및 사용자 식별 시나리오

## SC-01. 일반 고객이 로봇 앞에 접근
**상태:** [현재 핵심 흐름]

### 전제
- 로봇이 대기 상태이다.
- 이전 고객 세션이 종료되었다.

### 흐름
1. 카메라가 새로운 고객을 감지한다.
2. 로봇이 새 주문 세션을 시작한다.
3. 로봇이 웃는 표정과 인사 동작을 출력한다.
4. 로봇: **“안녕하세요. 주문 도와드릴게요.”**
5. TTS가 끝난 뒤 사용자 음성을 받을 준비 상태로 전환한다.

### 기대 상태
- Decision: `START_ORDER`
- 대화 상태: `ORDER_LISTEN`
- 표정: `SMILE`
- 고개: `NOD`
- 다음 입력: 고객 주문 음성

---

## SC-02. 등록되지 않은 고객 또는 얼굴 인식 불확실
**상태:** [연동 흐름]

1. 사람은 감지되지만 등록 고객으로 확정할 만큼 얼굴 매칭 신뢰도가 높지 않다.
2. 로봇은 이름·선호 메뉴 등 개인정보 기반 응대를 하지 않는다.
3. 일반 고객 흐름 SC-01로 전환한다.

### 원칙
- **얼굴 인식이 애매하면 개인화하지 않는다.**
- 오인식보다 일반 주문 전환을 우선한다.

---

## SC-03. 단골 고객이 방문
**상태:** [연동 흐름]

### 전제
- 고객이 앱에서 얼굴 등록 및 개인정보 활용 동의를 완료했다.
- 얼굴 특징 정보와 선호/주문 이력이 저장되어 있다.

### 흐름
1. 카메라가 고객 얼굴을 감지한다.
2. Face Embedding을 추출한다.
3. 등록 고객 정보와 비교한다.
4. 신뢰도가 충분하면 고객 정보를 조회한다.
5. 로봇이 개인화 인사를 제공한다.
6. 예: **“오랜만에 오셨네요. 항상 주문하시던 아이스 아메리카노로 준비할까요?”**
7. 고객 응답에 따라 분기한다.

### 고객이 “네” 또는 끄덕임
- 추천 메뉴를 주문 후보로 구성한다.
- 바로 확정하지 않고 주문 내용 확인 절차로 이동한다.

### 고객이 “아니요” 또는 좌우 흔들기
- 추천을 폐기한다.
- 일반 음성 주문 SC-01/SC-04 흐름으로 전환한다.

# 4. 정상 음성 주문 시나리오

## SC-04. 단일 메뉴를 완전하게 말한 경우
**상태:** [현재 핵심 흐름]

### 사용자
**“아이스 아메리카노 두 잔 주세요.”**

### 인식 결과
- 메뉴: 아메리카노
- 온도: ICE
- 수량: 2

### 흐름
1. STT가 음성을 텍스트로 변환한다.
2. NLU가 주문 정보를 추출한다.
3. 필수 정보가 모두 있으므로 추가 질문을 하지 않는다.
4. 로봇: **“아이스 아메리카노 2잔 맞으신가요?”**

### 기대 상태
- Decision: `CONFIRM_ORDER`
- 다음 입력: 승인/부정/정정

---

## SC-05. 온도를 말하지 않은 경우
**상태:** [현재 핵심 흐름]

### 사용자
**“아메리카노 한 잔 주세요.”**

### 판단
- 메뉴: 아메리카노
- 수량: 1
- 온도: 누락
- 아메리카노는 HOT/ICE 모두 가능 → 임의 결정 금지

### 로봇
**“아메리카노는 아이스로 드릴까요, 따뜻하게 드릴까요?”**

### 사용자
**“아이스로요.”**

### 결과
- 온도 = ICE로 현재 항목에 결합
- 로봇: **“아이스 아메리카노 1잔 맞으신가요?”**

### 기대 상태
- 누락 시 `ASK_TEMPERATURE`
- 보완 후 `CONFIRM_ORDER`

---

## SC-06. 수량을 말하지 않은 경우
**상태:** [현재 핵심 흐름]

### 사용자
**“아이스 아메리카노 주세요.”**

### 판단
- 메뉴와 온도는 있음
- 수량은 없음
- **기본값 1잔을 넣지 않는다.**

### 가능한 현재 흐름
메뉴와 온도가 충분히 명확하고 수량만 빠진 경우 `CONFIRM_ITEM`을 먼저 거칠 수 있다.

로봇: **“아이스 아메리카노 맞으신가요?”**

- 고객이 네/끄덕임 → **“아이스 아메리카노는 몇 잔 주문하시겠어요?”**
- 고객이 아니요/좌우 흔들기 → 현재 입력을 버리고 주문을 다시 받는다.

### 사용자
**“세 잔이요.”**

### 결과
- 수량 = 3
- 로봇: **“아이스 아메리카노 3잔 맞으신가요?”**

---

## SC-07. 메뉴를 말하지 않은 경우
**상태:** [현재 핵심 흐름]

### 사용자 예시
**“아이스로 두 잔 주세요.”**

### 판단
- 수량/온도 정보가 있어도 메뉴가 없음

### 후속
사용자가 메뉴를 말하면 기존에 유효하게 확보된 슬롯과 결합 가능한지 판단한 뒤 나머지 누락 슬롯을 계속 확인한다.

# 5. 다중 수량 및 복수 메뉴 시나리오

## SC-09. 한 메뉴를 여러 잔 주문
**상태:** [현재 핵심 흐름]

### 사용자
**“아이스 아메리카노 세 잔 주세요.”**

### 결과
- 하나의 주문 item
- `quantity = 3`
- 로봇: **“아이스 아메리카노 3잔 맞으신가요?”**

### 수량 표현
`세 잔`, `셋`, `3잔` 등 자연어 수량 표현을 현재 주문 수량으로 정규화한다.

---

## SC-10. 수량 질문에 짧게 답함
**상태:** [현재 핵심 흐름]

### 로봇
**“아이스 아메리카노는 몇 잔 주문하시겠어요?”**

### 사용자
**“세 잔이요.”**

### 판단
현재 `waiting_for = {item_id: 현재항목, slot: quantity}`이므로 “세 잔”은 현재 질문 중인 메뉴의 수량으로만 적용한다.

### 결과
- 기존 메뉴/온도 정보 유지
- 해당 item 수량만 3으로 갱신

## SC-11. 복수 메뉴를 한 문장에 완전하게 주문
**상태:** [현재 핵심 흐름]

### 사용자
**“아이스 아메리카노 두 잔하고 따뜻한 카페라떼 한 잔 주세요.”**

### NLU 구조
- item 0: 아메리카노 / ICE / 2
- item 1: 카페라떼 / HOT / 1

### 로봇
**“아이스 아메리카노 2잔, 따뜻한 카페라떼 1잔 맞으신가요?”**

Item Query 기반 구조를 통해 메뉴별 온도와 수량을 각각 묶어 관리한다.

---

## SC-12. 복수 메뉴에서 각 메뉴의 온도가 누락
**상태:** [현재 핵심 흐름]

### 사용자
**“아메리카노랑 카페라떼 하나씩 주세요.”**

### 흐름
1. 두 item 모두 수량=1로 인식된다.
2. 두 메뉴 모두 HOT/ICE 선택이 필요하다.
3. item_id 순서대로 질문한다.

로봇: **“아메리카노는 아이스로 드릴까요, 따뜻하게 드릴까요?”**  
사용자: **“따뜻하게요.”**

로봇: **“카페라떼는 아이스로 드릴까요, 따뜻하게 드릴까요?”**  
사용자: **“아이스로요.”**

로봇: **“따뜻한 아메리카노 1잔, 아이스 카페라떼 1잔 맞으신가요?”**

---

## SC-13. 복수 메뉴에 공통 옵션을 한 번에 말함
**상태:** [현재 핵심 흐름]

### 사용자
**“아메리카노랑 카페라떼 하나씩 주세요.”**

로봇이 온도를 묻는 중:

### 사용자
**“둘 다 아이스로요.”**

### 판단
- 대상이 명확한 공통 표현
- `apply_to_all_items = true`
- 두 item의 온도를 ICE로 채움

### 결과
**“아이스 아메리카노 1잔, 아이스 카페라떼 1잔 맞으신가요?”**

### 허용 가능한 대표 표현
- 둘 다 아이스로
- 전부 따뜻하게
- 각각 한 잔씩
- 전부 두 잔씩

대상이 모호하면 일괄 적용하지 않는다.

---

## SC-14. 복수 메뉴 중 일부 정보만 누락
**상태:** [현재 핵심 흐름]

### 사용자 예시
**“아이스 아메리카노 두 잔이랑 카페라떼 한 잔 주세요.”**

### 판단
- 아메리카노: 완성
- 카페라떼: 온도 누락

### 로봇

**“카페라떼는 아이스로 드릴까요, 따뜻하게 드릴까요?”**

응답 후 전체 주문을 한 번에 최종 확인한다.

## SC-19. 확인 질문에 바로 자연어로 정정
**상태:** [현재 핵심 흐름]

로봇: **“아이스 아메리카노 1잔 맞으신가요?”**  
사용자: **“아이스 아메리카노 두 잔이요.”**

### 판단
사용자가 반드시 “수정할게요”라고 말할 필요는 없다. 확인 상태에서 명확한 새 주문 정보를 말하면 기존 item의 수정으로 처리할 수 있다.

### 결과
- 수량 1 → 2로 변경
- 다시 `CONFIRM_ORDER`
- 로봇: **“아이스 아메리카노 2잔 맞으신가요?”**

---

## SC-20. 복수 메뉴 수정 대상이 모호함
**상태:** [현재 핵심 흐름]

# 8. STT/NLU 및 입력 예외 시나리오

## SC-27. STT가 사용자의 말을 듣지 못함
**상태:** [현재 핵심 흐름]

### 예외 예
- 무음 `empty`
- 목소리가 너무 작음 `too_quiet`
- 인식 거부 `rejected`
- 마이크/인식 오류

### 처리
1. 잘못된 주문으로 확정하지 않는다.
2. 재질문 음성·질문 표정으로 다시 입력을 요청한다.
3. STT를 재실행한다.
4. 재시도 한도를 넘으면 음성 인식 실패를 안내하고 복구 흐름으로 전환한다.

---

## SC-28. NLU 신뢰도가 낮거나 주문 의미가 불명확
**상태:** [현재 핵심 흐름]

### 사용자 예
- “음…”
- “저기…”
- 주문과 관계없는 불명확 발화

### 처리
- `needs_reprompt = true` 또는 낮은 confidence이면 주문 확정 금지
- 1~2회: `REPROMPT`
- 반복 실패로 재질문 한도 소진: `REORDER_REQUEST`

### 핵심
AI가 확신하지 못하는 값을 임의로 주문에 넣지 않는다.

# 10. 사전 주문 고객 시나리오

3. 다른 본인 확인 수단으로 재확인한다.
4. 그래도 확인이 불가능하면 타인의 주문 정보를 노출하지 않는다.

3. 관리자 화면에 알림을 제공한다.

# 14. 통합 테스트 체크리스트

각 시나리오 테스트 시 다음 항목을 함께 확인한다.

- [ ] 사람 접근이 한 세션에 한 번만 인사로 이어지는가
- [ ] TTS가 끝나기 전에 STT가 열리지 않는가
- [ ] 사용자에게 말할 타이밍이 화면/로그에 명확히 표시되는가
- [ ] 메뉴/수량/온도 누락을 임의값으로 채우지 않는가
- [ ] ICE 전용 메뉴에서 불필요한 온도 질문이 나오지 않는가
- [ ] 짧은 후속 답변이 현재 `waiting_for` item/slot에 정확히 적용되는가
- [ ] 복수 메뉴의 온도·수량이 서로 섞이지 않는가
- [ ] “둘 다”, “각각” 같은 공통 표현이 명확할 때만 일괄 적용되는가
- [ ] 주문 확인에서 네/아니요와 NOD/SHAKE가 동일 정책으로 작동하는가
- [ ] 확인 단계에서 자연어 정정이 가능하고 수정 후 재확인하는가

## 16. 핵심 설계 원칙 요약

Pumpkin의 대화 정책은 다음 한 문장으로 요약할 수 있다.

> **모델이 추측해서 주문을 완성하지 않고, 확실한 정보만 저장하며, 부족하거나 모호한 정보는 현재 대화 상태와 주문 항목을 기준으로 다시 물은 뒤 최종 확인을 거쳐 주문한다.**

이 원칙은 일반 고객, 단골 고객, 단일 주문, 다중 수량, 복수 메뉴, 음성 응답, 고개 제스처, 사전 주문 모두에 동일하게 적용한다.
