# NLU 재학습 데이터 보강 가이드

이 문서는 Pumpkin 주문 로봇의 다음 NLU 모델을 만들 때 반드시 추가해야 할 데이터 유형과 라벨링 원칙을 정리한다.

현재 운영 모델은 한 문장만 입력받아 `intent`, `order_status`, 최대 3개의 주문 item(`menu`, `temperature`, `quantity`)을 예측한다. 대화 상태와 이전 주문 item은 NLU 모델이 아니라 FSM이 관리한다. 따라서 짧은 후속 답변에는 이전 메뉴를 임의로 복사하지 않고, 사용자가 이번 발화에서 직접 말한 슬롯만 라벨링해야 한다.

## 1. 현장 오류에서 확인된 우선 보강 항목

| 우선순위 | 데이터 유형 | 실제 또는 대표 발화 | 목표 |
|---|---|---|---|
| P0 | 누락 슬롯 질문 뒤 짧은 답변 | `따뜻하게요`, `아이스요`, `한 잔이요` | 문맥 없는 짧은 발화에서도 직접 표현된 슬롯 추출 |
| P0 | 추가 주문 요청 | `하나 더 주문할게요`, `추가 주문할래요` | 기존 주문 수정과 신규 item 추가 의도 구분 |
| P0 | 명시 다중 메뉴 주문 | `레모네이드랑 아메리카노 차갑게 하나씩 주세요` | 메뉴 순서, 공통 온도, 공통 수량 인식 |
| P0 | 발화 앞부분 잡음·군더더기 | `어 아메리카노 하나요`, `으음 레몬에이드 주세요` | 문장 앞에 짧은 비의미 토큰이 붙어도 핵심 주문 유지 |
| P1 | 주문 종료 여부 응답 | `네`, `아니요`, `더 주문할게요` | FSM 상태와 결합했을 때 종료·계속 주문 분기 안정화 |
| P1 | 수정·취소의 자연어 변형 | `아메리카노 말고 라떼로요`, `방금 거 취소할게요` | MODIFY/CANCEL 표현 다양화 |
| P1 | STT 오인식형 텍스트 | 띄어쓰기 오류, 반복 음절, 일부 조사 누락 | 실제 음성 입력에서 발생하는 텍스트 변형 강건성 확보 |

## 2. 누락 슬롯 질문 뒤 짧은 답변

다음 유형은 기존 완전 주문 문장과 별도로 충분히 추가해야 한다.

### 2.1 온도만 말한 답변

예시:

```text
따뜻하게요
뜨거운 걸로요
핫이요
아이스요
차갑게 주세요
찬 걸로 할게요
```

권장 라벨 예시:

```json
{
  "text": "따뜻하게요",
  "intent": "ORDER",
  "order_status": "INCOMPLETE",
  "items": [
    {
      "menu": null,
      "temperature": "HOT",
      "quantity": null
    }
  ]
}
```

중요:

- 이전 질문이 `아메리카노는 아이스로 드릴까요, 따뜻하게 드릴까요?`였더라도 NLU 데이터에 `menu=아메리카노`를 넣지 않는다.
- 메뉴 연결은 FSM의 `waiting_for.item_id`가 담당한다.
- `따뜻하게요`와 `아이스요`가 단독 입력일 때도 해당 온도 슬롯을 안정적으로 추출해야 한다.

### 2.2 수량만 말한 답변

예시:

```text
한 잔이요
하나요
두 잔 주세요
세 개요
그거 두 잔이요
```

권장 라벨 예시:

```json
{
  "text": "두 잔이요",
  "intent": "ORDER",
  "order_status": "INCOMPLETE",
  "items": [
    {
      "menu": null,
      "temperature": null,
      "quantity": 2
    }
  ]
}
```

### 2.3 메뉴만 말한 답변

예시:

```text
아메리카노요
레모네이드요
딸기스무디로 할게요
라떼 주세요
```

권장 라벨 예시:

```json
{
  "text": "레모네이드요",
  "intent": "ORDER",
  "order_status": "INCOMPLETE",
  "items": [
    {
      "menu": "레몬에이드",
      "temperature": null,
      "quantity": null
    }
  ]
}
```

### 2.4 질문-답변 문맥별 테스트 표

학습 데이터에는 사용자 답변만 넣되, 평가 문서는 어떤 FSM 질문 뒤에 사용되는지 함께 관리한다.

| FSM 질문 | 사용자 답변 | NLU가 추출할 값 |
|---|---|---|
| `어떤 메뉴로 주문하시겠어요?` | `아메리카노요` | menu=아메리카노 |
| `몇 잔 주문하시겠어요?` | `두 잔이요` | quantity=2 |
| `아이스로 드릴까요, 따뜻하게 드릴까요?` | `따뜻하게요` | temperature=HOT |
| `주문 내용이 맞으신가요?` | `네 맞아요` | intent=AFFIRM |
| `주문을 마치시겠어요?` | `아니요, 하나 더요` | 추가 주문 의미 |

## 3. 추가 주문 데이터

현재 intent 라벨에는 `ADD_ORDER`가 없다. 다음 모델을 만들 때는 아래 두 방식 중 하나를 명확히 선택해야 한다.

### 권장 방식: `ADD_ORDER` intent 추가

다음 표현은 주문 수정(MODIFY)과 의미가 다르므로 별도 intent가 가장 명확하다.

```text
하나 더 주문할게요
추가 주문할래요
음료 하나 더 주세요
더 주문할게요
하나 더 시킬게요
추가로 레몬에이드 하나요
그리고 아메리카노도 하나 주세요
```

권장 라벨:

```json
{
  "text": "하나 더 주문할게요",
  "intent": "ADD_ORDER",
  "order_status": "NONE",
  "items": []
}
```

메뉴가 함께 나온 경우:

```json
{
  "text": "추가로 레몬에이드 하나요",
  "intent": "ADD_ORDER",
  "order_status": "VALID",
  "items": [
    {
      "menu": "레몬에이드",
      "temperature": "ICE",
      "quantity": 1
    }
  ]
}
```

주의:

- `ADD_ORDER`를 모델에 추가하면 Decision Node와 label map도 함께 지원해야 한다.
- 모델에 라벨만 추가하고 FSM 분기를 추가하지 않으면 운영 환경에서 `UNKNOWN` 또는 잘못된 수정 흐름으로 이어질 수 있다.

### 기존 스키마 유지 방식

현재 스키마를 유지해야 한다면 추가 주문 문장은 FSM의 명시적 표현 규칙으로 처리하고, NLU 학습 데이터에서는 별도 회귀 평가 세트로 관리한다. 이 경우 `MODIFY`로 억지 라벨링하지 않는다. `기존 item 변경`과 `새 item 추가`가 섞이면 모델과 FSM의 의미가 불일치하기 때문이다.

## 4. 다중 주문과 공통 표현

다음 패턴을 충분히 추가한다.

### 4.1 공통 수량

```text
아메리카노랑 라떼 하나씩 주세요
레몬에이드하고 딸기스무디 두 잔씩이요
세 메뉴 모두 한 잔씩 주세요
각각 두 개 주세요
```

기대 결과:

- `하나씩`, `두 잔씩`, `각각`, `모두`, `전부`, `둘 다`의 범위를 정확히 반영한다.
- 공통 수량이 모든 활성 item에 적용된다.

### 4.2 공통 온도

```text
아메리카노랑 라떼 둘 다 아이스로요
두 음료 모두 따뜻하게 주세요
전부 차갑게 해주세요
```

### 4.3 메뉴별 서로 다른 옵션

```text
아메리카노는 뜨겁게 한 잔, 라떼는 아이스로 두 잔 주세요
레몬에이드는 하나, 아메리카노는 따뜻하게 두 잔 주세요
```

### 4.4 메뉴 별칭과 혼동쌍

특히 다음 혼동을 집중 보강한다.

```text
레몬에이드 / 레모네이드
카페라떼 / 카페라테 / 라떼
바닐라라떼 / 바닐라라테
아메리카노 / 아메 / 아아 / 뜨아
딸기스무디
```

모든 메뉴가 item 0, item 1, item 2 위치에 비슷한 비율로 등장하도록 한다. 특정 메뉴가 첫 번째 item에만 자주 나오면 Item Query가 위치 편향을 학습할 수 있다.

## 5. 문장 앞 잡음과 군더더기 대응

NLU는 오디오가 아니라 STT가 출력한 텍스트를 입력받는다. 따라서 카페 소리 자체를 NLU 데이터에 넣는 것이 아니라, 실제 잡음 때문에 STT 결과에 생기는 텍스트 변형을 추가해야 한다.

### 5.1 NLU용 텍스트 증강

원문과 같은 라벨을 유지하는 앞부분 군더더기 예시:

```text
아메리카노 하나요
어 아메리카노 하나요
음 아메리카노 하나요
으음 아메리카노 하나요
아 저 아메리카노 하나요
네 저기 아메리카노 하나요
그 아메리카노 하나 주세요
저기요 아메리카노 하나요
```

복합 주문 예시:

```text
어 레모네이드랑 아메리카노 하나씩 주세요
음 저 레몬에이드하고 라떼 둘 다 차갑게요
아 그 아메리카노는 따뜻하게 라떼는 차갑게 주세요
```

추가할 변형:

- 맨 앞 1~3개의 짧은 추임새: `어`, `음`, `아`, `으음`, `저`, `저기`, `그`
- 반복: `어 어`, `음음`, `저 저기`
- 비정상 띄어쓰기: `아메리카노하나요`, `하나 씩`, `차갑 게`
- 조사 누락: `아메리카노 하나`, `라떼 아이스 두 잔`
- STT가 자주 만드는 실제 오인식 철자

금지:

- 실제 STT가 출력하지 않는 `[잡음]`, `<noise>` 같은 가상 토큰을 무조건 넣지 않는다.
- 문장의 의미를 바꿀 정도로 임의 음절을 과도하게 추가하지 않는다.
- 동일한 증강 템플릿을 수천 번 복제해 전체 데이터 분포를 왜곡하지 않는다.

### 5.2 반드시 실제 로그 기반으로 만들기

Jetson 현장 테스트에서 다음을 함께 저장한다.

```text
원래 말한 문장
STT가 출력한 문장
NLU 예측
정답 라벨
주변 소음 종류
```

예시:

```json
{
  "spoken_text": "아메리카노 하나요",
  "stt_text": "어 아메리카노 하나요",
  "noise_type": "카페 배경음",
  "expected_intent": "ORDER",
  "expected_items": [
    {
      "menu": "아메리카노",
      "temperature": null,
      "quantity": 1
    }
  ]
}
```

실패한 STT 문장은 추측해서 만들기보다 실제 로그에서 수집한 표현을 우선한다.

### 5.3 오디오 잡음은 STT 쪽에서도 별도 보강

문장 앞에 실제 소리가 한 번 섞였을 때 STT 자체가 틀린다면 NLU 재학습만으로 완전히 해결할 수 없다. Faster-Whisper 평가용 음성 데이터에도 다음 조건을 추가한다.

- 카페 대화음, 컵 소리, 기계 소리, 팬 소음
- 시작 0.1~0.5초의 짧은 충격음 또는 말 겹침
- 로봇 TTS 잔향과 사용자 발화가 일부 겹치는 경우
- 가까운 거리와 먼 거리 녹음
- 작은 목소리와 빠른 발화
- SNR별 평가 세트

오디오 증강본과 원본은 서로 다른 split으로 나누지 않는다. 같은 원본에서 만든 변형은 반드시 같은 split에 둔다.

## 6. 긍정·부정·종료·수정 표현 보강

### 6.1 긍정

```text
네
넵
예
응
맞아요
맞습니다
그대로 주세요
그렇게 해주세요
좋아요
확인했어요
```

### 6.2 부정 및 수정 진입

```text
아니요
그거 아니에요
틀렸어요
바꿀게요
수정할게요
다시 말할게요
아메리카노 말고 라떼요
아이스 말고 따뜻하게요
두 잔 말고 한 잔이요
```

### 6.3 주문 종료 여부

로봇 질문이 `주문을 마치시겠어요?`일 때 다음 표현을 별도 시나리오 테스트로 관리한다.

```text
네, 끝이에요
네 다 했어요
이제 됐어요
주문 마칠게요
아니요
아직이요
하나 더 주문할게요
추가할게요
```

현재 NLU는 대화 상태를 입력받지 않으므로 `네` 자체는 항상 AFFIRM, `아니요` 자체는 항상 DENY로 라벨링한다. 실제 의미는 FSM 상태가 결정한다.

## 7. 질문형 고객 발화

고객이 주문 대신 질문하는 표현도 추가한다.

```text
어떤 메뉴가 있어요?
따뜻한 음료는 뭐가 있어요?
레몬에이드도 따뜻하게 되나요?
아메리카노 아이스로 가능한가요?
한 번에 몇 잔까지 주문할 수 있어요?
결제는 어디서 해요?
카드는 되나요?
```

라벨 원칙:

- 메뉴·옵션 안내 질문은 프로젝트 정책에 따라 GUIDE 또는 별도 `MENU_QUERY` intent를 사용한다.
- 결제 질문은 PAYMENT로 라벨링한다.
- 질문 안에 메뉴 이름이 있다고 해서 주문 item을 생성하지 않는다.
- `아메리카노 하나 가능해요?`처럼 주문과 질문의 경계가 애매한 문장은 별도 애매성 세트로 관리한다.

다음 모델에서 메뉴 질문 응답까지 제대로 지원하려면 `MENU_QUERY` 또는 `OPTION_QUERY` intent를 추가하는 것이 더 명확하다. 이 경우에도 FSM과 응답 관리자 변경이 함께 필요하다.

## 8. 데이터 생성 수량 권장안

다음은 최소 보강 목표다. 기존 30,036개 데이터에 단순 비율로 섞지 말고, 부족한 slice를 의도적으로 채운다.

| 데이터 slice | 최소 추가 권장량 |
|---|---:|
| 온도만 있는 짧은 답변 | 600 |
| 수량만 있는 짧은 답변 | 600 |
| 메뉴만 있는 짧은 답변 | 500 |
| 긍정·부정 짧은 답변 | 500 |
| 추가 주문 요청 | 800 |

| 질문형 고객 발화 | 600 |

같은 문장을 단어 하나만 바꿔 대량 복제하기보다 메뉴, 수량, 온도, 어순, 말투를 조합하되 자연스러운 문장인지 사람이 검수한다.

## 9. train/valid/test 분할 원칙

1. 기존 split을 임의로 다시 섞지 않는다.
2. 새 데이터를 추가할 때도 train/valid/test 출처를 명시한다.
3. 같은 원문에서 생성한 잡음 변형과 패러프레이즈는 모두 같은 split에 둔다.
4. 템플릿이 거의 같은 문장을 train과 test에 나누지 않는다.
5. 실제 현장 실패 문장 일부는 학습에 넣지 않고 고정 회귀 test set으로 보존한다.
6. 메뉴, 온도, 수량, item 위치별 분포를 split마다 확인한다.
7. test set은 최종 모델 선택에 사용하지 않는다.

권장 추가 평가 파일:

```text
data/eval/nlu_followup_short_answers.jsonl
data/eval/nlu_additional_order.jsonl
data/eval/nlu_noisy_prefix.jsonl
data/eval/nlu_real_stt_failures.jsonl
```

## 10. 평가 지표

전체 평균 정확도만 확인하면 소수 실패 유형이 가려질 수 있다. 다음 slice별 지표를 별도로 기록한다.

- Intent accuracy 및 macro F1
- Order status accuracy
- Item active accuracy
- Menu/temperature/quantity slot accuracy
- 전체 frame accuracy
- 짧은 온도 답변 exact match
- 짧은 수량 답변 exact match
- 추가 주문 intent recall
- clean/noisy pair prediction consistency
- 다중 주문 item 순서 정확도
- 실제 STT 실패 회귀 세트 통과율

권장 합격 기준 예시:

```text
짧은 온도·수량 답변 slot accuracy >= 98%
추가 주문 intent recall >= 95%
앞부분 군더더기 clean/noisy 일치율 >= 97%
실제 현장 회귀 문장 100% 통과
기존 test frame accuracy 하락 <= 0.5%p
```

## 11. 재학습 전 체크리스트

- [ ] `따뜻하게요`, `아이스요`, `한 잔이요`가 단독 데이터로 포함되어 있는가?
- [ ] 짧은 답변에 이전 메뉴를 잘못 복사하지 않았는가?
- [ ] 추가 주문을 MODIFY와 구분할 정책이 결정되었는가?
- [ ] 새 intent를 추가했다면 FSM과 label map도 수정했는가?
- [ ] `하나씩`, `각각`, `둘 다`, `모두`, `전부`가 충분히 포함되어 있는가?
- [ ] 메뉴 별칭과 혼동쌍이 item 위치별로 균형적인가?
- [ ] 문장 앞 추임새와 실제 STT 오류 문장이 포함되어 있는가?
- [ ] 오디오 잡음 문제를 NLU와 STT 데이터로 구분해 대응했는가?
- [ ] 같은 원문의 증강본이 split을 넘나들지 않는가?
- [ ] 현장 실패 문장을 고정 회귀 평가 세트에 남겼는가?
- [ ] 전체 점수뿐 아니라 slice별 성능을 기록했는가?
